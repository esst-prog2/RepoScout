# PROCESS.md — Promo page

How RepoScout's promo page on GitHub Pages was made: one row per step, written right after the step and committed with it.

| # | Step | What the tool did | What I decided |
|---|------|-------------------|----------------|
| 1 | Set the working rule (Claude Code) | Created this file and the `promo-page` branch from the updated `main`, saved the rule ("after each step: commit + a row here") so it applies for the rest of the work, and committed. Checked that the repo is public. | Every step from now on ends with a commit and a row here. GitHub Pages source = "GitHub Actions" (set in the repo settings), not the suggested Jekyll / Static HTML templates. |
| 2 | Content, with gstack `/office-hours` | Ran office hours in builder mode (goal: class demo). Asked one question at a time, searched what good dev-tool landing pages do (specific claims, two calls to action, try without sign-up), checked 5 premises, offered 3 page structures, wrote the full draft copy, and had an independent reviewer check it twice (round 1: 1 blocking problem, the cache-busting plan missed the `rules.js` import; fixed; round 2: pass, 10 small notes). Saved as `docs/designs/promo-page.md`. | Hook: **alive vs. graveyard** (the 26 Oct `mcp server` and `angularjs directive` screenshots side by side). For **people about to build**. Try it: **web app first, command line second**. English. Structure **B**: hero, who it's for, how to read a result, try it, honest limits. No invented users or quotes. Approved, with all 10 reviewer notes folded in (trace explained, shared-Wi-Fi rate limit, venv step, softer CSV wording, app at `/app/`). |
| 3 | The look, part 1: Impeccable `shape` | Loaded the project's design context (PRODUCT.md, the app's DESIGN.md "ECG printout" world, the content doc), looked at the screenshots, asked 3 questions, and wrote a design brief without code: Persuade mode, the app's world inherited, the hero as two stacked "ECG leads" cut from the 26 Oct screenshots with the verdicts as real text, a one-time left-to-right reveal, section order, phone layout, anti-goals. Saved as `docs/designs/promo-page-brief.md`. | Same visual world as the app (not a separate promo look). Hero = **two stacked ECG leads** (`mcp server` beating above, `angularjs directive` flatlining below). What would feel wrong: **salesy / hype**, so no superlatives, exclamation marks, badges or testimonials. Confirmed the brief. The hero's exact arrangement is left for `generate`. |
| 4 | Plan the build: OpenSpec `/opsx:propose` | Created the change `promo-page-on-github-pages`: proposal, two new specs (`promo-page`: what/who/how-to-try, links, evidence-only numbers, honest limits, phone width, nothing personal; `pages-publishing`: promo at the root and the app under `/app/`, nothing else published, cache-busting of the published copies, deploy only after tests pass), a design and 13 tasks. Validated with `openspec validate --strict`. | One Python script (`scripts/build_pages.py`) assembles the site for both the local preview and the deploy, so what I preview is what gets published. Our own Actions workflow, not the suggested templates. The hero images are crops of the 26 Oct screenshots. `generate` and `critique` run on the first built version. |
| 5 | Instructor's "before you publish" rules applied to the plan | Checked what would be published: the app's files have no names, e-mail addresses or paths; Pages publishes only the assembled folder, never the git history (commit authors use a GitHub noreply address). Found that screenshot 4 (the table) shows GitHub account names, some of them people's names. Updated the OpenSpec change: blurred copy of screenshot 4 for the page, the original never published, and a personal-data test over every published text file. | Blur the account part of each repository name in the table image; keep everything else readable. The original screenshot stays untouched (no retake). |
| 6 | Build the first version (`/opsx:apply`, tasks 1–2) | Wrote the tests first, then `scripts/build_pages.py`: it puts the promo page at the root and the app under `app/`, adds `?v=` to stylesheet and script links and to the `rules.js` import in the copies only, and refuses to publish an e-mail address or a local path. Cut the two hero strips from the 26 Oct screenshots and made a copy of the table with every account name blurred (checked at 3× zoom). Wrote `promo/index.html` and `promo/style.css` in the app's ECG look. Checked it in a real browser: at 1440×900 the hero and the whole first strip fit on the first screen; at 360 px nothing scrolls sideways; focus rings are visible; "Open RepoScout" opens the app under `app/` and a live search works. 210 Python tests pass (31 new). | On phones each strip scrolls sideways and opens at "now", where alive and dead differ, instead of shrinking to an unreadable size. The verdicts are real text above the images. |
| 7 | Publish setup: the deploy workflow and docs (tasks 4, 5.1) | Looked up the current release of each official GitHub Pages action and pinned them exactly (checkout v7.0.1, setup-python v7.1.0, setup-node v7.1.0, configure-pages v6.0.0, upload-pages-artifact v5.0.0, deploy-pages v5.0.1). Wrote `.github/workflows/pages.yml`: on every push to `main` (or a manual start) it runs the Python and JavaScript tests, assembles the site with the commit as cache-busting version, and uploads only `_site/`. Added the live addresses and the preview command to the user manual, and updated PRODUCT.md. | Publishing happens only after merging to `main`, so the branch can be reviewed first. Nothing goes online before the PR is merged. |
| 8 | Hero variants (`/impeccable generate`, direction: bolder) | Opened the promo page in my browser with Impeccable's live overlay and built three bolder versions of the oxblood band: (1) scale: the question at full display size in narrower letters; (2) trace: one ECG line across the band under the buttons, flat over the old years and beating at "now"; (3) trace red: the band in the app's "active" red with "alive?" on its own line. After I picked one, it moved the chosen version into `promo/index.html` and `promo/style.css`, lined the trace's time labels up with the real strip's zones (1 year at 39%, 3 months at 75%), and re-checked it in a browser at 1440 and 360 px (no sideways scroll). 210 Python + 66 JavaScript tests pass. | Chose variant 2, the trace across the band, with default height and time labels on: the headline's question gets the page's own heartbeat line as its first answer, before the real strips. Trade-off accepted: at 1440×900 the first screen now shows lead I's verdict and the top of its strip, not the whole strip. |
| 9 | Critique (`/impeccable critique`) and fixing its weakest part | Ran two independent checks: a design review (as a first-timer, a stress tester, a phone user, a classmate, the instructor and a stranger) and the automated detector plus browser measurements. Score 24/32 (Good). All text passes contrast, nothing scrolls sideways, headings and alt text are fine. **Weakest part: the illustrative trace in the band** (the hero I had just picked): a drawing of a chart directly above the real charts, with a slightly different time axis, pushing the first real strip below the first screen. Second problem: in "One search, four answers" the screenshots were too small to read and answer 2 sat under the wrong screenshot. Fixed both: removed the band trace (the first strip fits on a 1440×900 screen again, bottom at 885 px), cropped the two screenshots to the part that matters (verdict + strip; table top + Download CSV, account names still blurred) and put each one right above its own answers; on phones the number markers are hidden because they covered the shrunken text. 210 Python + 66 JavaScript tests pass. | Remove the band trace (the real strips are the proof; an imitation above them weakens them), and fix the weakest part plus the second big issue now. Left for later: split the command-line block into Windows / macOS-Linux, a light outline on the red button on the band, fewer repeated GitHub links. |
| 10 | Publish on GitHub Pages and push | Pushed the `promo-page` branch; I opened the PR and merged it. The Pages workflow ran on `main`: tests passed, the site was assembled and deployed. Checked live in a browser: https://esst-prog2.github.io/RepoScout/ shows the promo page (font, all 4 images, no sideways scroll at 360 px), CSS/JS links carry `?v=3029f51` including the `rules.js` import, and https://esst-prog2.github.io/RepoScout/app/ runs a real search ("expense tracker" → 251,410 repos, 4 active). | Publish from the course repo itself with Pages source "GitHub Actions" (no fork), only after merging to `main`. |
| 11 | Critique fixes, round 2 (`/impeccable clarify`, `polish`, `distill`, then `critique` again) | Split the command line into a Windows (PowerShell) block and a macOS/Linux block; gave the red button a light edge on the oxblood band (now 6:1 against the band, was 2.4:1); made "Two real searches, 26 October 2026" a visible label above the strips (it replaces the cramped date line underneath) and tightened the band so the first strip still fits a 1440×900 screen (bottom at 898 px); turned the hero's "View the code on GitHub" button into a text link. The second critique scored 22/32, not directly comparable with round 1 (a different heuristic counted as n/a); every round-1 issue measured as fixed. It found a real bug: `.venv\Scriptsctivate` is blocked by PowerShell's default script policy (`Restricted` on this machine). Replaced it with `.\.venv\Scripts\python -m pip install .` and `.\.venv\Scripts\reposcout search ...`, tested in a fresh clone in Windows PowerShell, and added a test that the activate line can't come back. 210 Python + 66 JavaScript tests pass. | Fix the Windows commands and push. Left for later from round 2: a one-line strip key under the leads (with "One search, four answers" trimmed to the table and CSV, the new weakest part), the phone animation revealing the "now" end last, and fitting both leads on the first screen. |
| 12 | Close the change (`/opsx:archive`) | Checked that all 4 artifacts and 15/15 tasks are done, then turned the change's two new capabilities into main specs: `openspec/specs/promo-page/spec.md` (6 requirements) and `openspec/specs/pages-publishing/spec.md` (4 requirements); `openspec validate --specs --strict` passes (6/6).
