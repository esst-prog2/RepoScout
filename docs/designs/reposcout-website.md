## Problem Statement

RepoScout is a working Python CLI (`reposcout search "<keyword>"`): one GitHub Search API call, the 50 best-matching repos ranked by stars, each bucketed active / slowing / stale by `pushed_at`, a one-line verdict, a CSV, a 24h cache, 119 tests. The course's halftime ("if you're done, make it bigger") calls for a real interface. The final demo (1 or 8 December 2026) is a five-minute presentation with screenshots, not a live run, so the website must produce screens that explain themselves.

## What Makes This Cool

Existing repo-health tools judge one repo you already know. RepoScout judges a whole topic. The heartbeat strip shows that in one picture: every repo is a dot on a "last push" timeline, size = stars, shade = bucket, over background zones for stale / slowing / active. A crowded-and-alive topic clusters on the right; a graveyard fades to the left. It reads instantly on a projector or a slide screenshot.

- Demo is screenshots, not live: no audience load, no live rate-limit pressure during the talk.
- Runs on localhost now; may be published on GitHub Pages later with the same files.

## Premises

1. The heartbeat strip is the hero; verdict, table and CSV stay underneath it.
2. The Python CLI stays as it is and keeps its tests; the website is added, not a replacement.
3. Static files only (HTML + CSS + JavaScript), no build step and no server code, so the same files run on localhost and on GitHub Pages. (Pages' settings switch serves only the repo root or `/docs`; publishing `site/` therefore needs either moving the files under `docs/` or a small Pages workflow. Decided at publish time, see Open Questions.)
4. The web version is tokenless; the unauthenticated limit (10 searches/minute) is shown as a friendly countdown, not an error.
5. README section 1 "The demo" is rewritten for the website through `/opsx:propose` (this also covers HW8).
6. The bucket thresholds and verdict wording must not drift between Python and JavaScript.

## Approaches Considered

- **Prebaked + live hybrid** (nightly GitHub Action runs the Python, site renders JSON, plus a live box). Designed for classmates searching on their phones at once; dropped when the user clarified the demo is screenshots, not a live run.
- **Live-only static site on Pages / prebaked gallery without a live box**: superseded by the same clarification.
- **Python web app (Flask/FastAPI) on localhost**: reuses the Python modules directly, but GitHub Pages can't run Python, so "publish later" would mean a rewrite. Rejected for that reason.

## Recommended Approach

**Static HTML + JavaScript page, served on localhost, Pages-ready.** Chosen by the user (D2).

- `site/index.html`, `site/app.js`, `site/style.css`. Run locally with `python -m http.server` from `site/`. Publishing later: Pages' settings switch serves only the repo root or `/docs`, so either move the page under `docs/` or add a small Pages workflow (needs Actions allowed in the org).
- The browser calls `https://api.github.com/search/repositories?q=<keyword>&per_page=50` directly (CORS allowed, `Access-Control-Allow-Origin: *`, rate-limit headers exposed; verified 2026-10-25). No token.
- Same rules as the CLI: no `sort` (GitHub relevance picks the 50), display ranked by stars, buckets active < 90 days, slowing < 365, stale otherwise, verdict wording and round-down relative time identical to `output.py`.
- Heartbeat strip with Observable Plot. The pinned files (`@observablehq/plot` and the `d3` it needs, exact versions) are **vendored into `site/vendor/`**, so the page has no CDN dependency and works offline on localhost. If `Plot` is still missing at runtime, app.js renders the verdict and table anyway, with a plain "chart unavailable" note instead of the strip.
- **X-axis: piecewise, by bucket.** Three zones of readable width, ordered stale (left) to active (right). Each zone is linear in "days since last push" within its own range: active 0-90 days, slowing 90-365 days, stale 365 days up to 5 years, with anything older pinned at the left edge and labelled "5+ years". A plain linear time axis is rejected: over a 10-year spread the 90-day active zone would be about 2% of the width. Checked against a real "expense tracker" result while building, before it's final. Tooltip: name, stars, last push. One-line note that "Last push" is GitHub's `pushed_at`, not a verified last commit.
- Table (same columns as the CLI) and a "Download CSV" button that builds the CSV in the browser, with the same columns and filename rule as the CLI (`<slug>-report.csv`).
- States: loading, zero results, incomplete results, rate-limited, offline / other errors. All plain-language.
  - **Incomplete results:** when GitHub's response has `incomplete_results: true`, the page shows a warning that the results may be incomplete (same as the CLI).
  - **Rate-limited, same detection rule as the CLI:** primary limit = `X-RateLimit-Remaining: 0`; secondary limit = HTTP 403 or 429 with a `Retry-After` header. Count down from `Retry-After` when present, otherwise from `X-RateLimit-Reset`; when neither is present, say GitHub didn't give a reset time, with no countdown (never an invented time). Both headers are in GitHub's CORS-exposed list (verified 2026-10-25), so the browser can read them.
- Cache in the browser (`localStorage`, 24h, keyed by the normalized query) so repeat searches don't use the limit. The cache entry stores the `incomplete` flag, so a cache hit also shows the warning; an entry without the flag is treated as a miss (refetched), as in the CLI. Wrapped so the page still works if storage is unavailable.
- **One source for the rules.** The thresholds, the verdict template and the expected outputs live in a shared fixture (e.g. `tests/fixtures/rules.json`): Python tests and a small JavaScript test (`node --test`, no extra dependency; Node 24 is installed) both assert against it, so a change in one language without the other fails a test.
- Layout (wireframe approved 2026-10-25): title + one-line promise, search box, verdict sentence large, heartbeat strip, table + CSV button, state messages.

### R2-1 — clarity (minor)

**Problem**

> The primary-limit rule is not tied to a failed response. The CLI checks `_is_rate_limited()` only inside its handling of non-OK responses. A successful 200 can also carry `X-RateLimit-Remaining: 0`, for example on the 10th search of the minute. If someone implements the line literally, that search's valid results would be replaced by the rate-limited state. The phrase 'same detection rule as the CLI' points the right way, but the line itself doesn't say it.

**Remedy**

> Say that rate-limit detection runs only on non-OK responses (403/429). A 200 is always rendered as results, whatever its remaining count.

### R2-4 — feasibility (minor)

**Problem**

> The piecewise axis doesn't say how wide each zone is (equal thirds or something else), and it doesn't say how it gets built in Plot. Plot has no built-in piecewise scale with different units per segment. app.js would have to compute a derived x position and draw its own ticks and zone labels (0, 90 days, 1 year, 5+ years). The design doesn't mention that this extra work exists.

**Remedy**

> Choose the zone widths (e.g. equal thirds) and say that x is a precomputed position with custom ticks and labels per zone, so the 'about 15 lines' expectation is reset.
